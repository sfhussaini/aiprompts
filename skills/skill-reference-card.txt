# SKILL: story-to-prompt-converter


## 🎯 Overview


This skill performs **[Idea-to-Prompt Transformation]** to achieve **[Production-Ready Image Generation Pipeline]**.


### Capabilities
- **Primary:** Transform raw user ideas into structured story text (`story.txt`) and fragmented JSON buffers (iteratively).
- **Secondary:** Apply frame selection logic (Peak/First-Middle-Last) and finalize image prompts using weighted scoring templates.
- **Output Format:** `output/final-frames.json` containing flattened prompt data for generation engines.
- **Key terms:**
    - **Clip:** one continuous story beat (one location, one dramatic moment), about 2-4 sentences of story text.
    - **Frame:** one still image inside a clip, described precisely enough to generate. Each clip has several candidate frames.
    - **Peak (`best`):** the single highest-action or highest-emotion frame per clip. Selects 1 frame per clip.
    - **First-Middle-Last (`firstmiddlelast`):** the opening, midpoint, and closing frame of each clip. Selects 3 frames per clip.
    - **Character bible:** fixed visual descriptors for each recurring character and location, reused verbatim in every prompt.


### Constraints (When NOT to use)
- The user wants a single standalone image prompt with no story structure (write the prompt directly instead).
- The user wants the images themselves generated (this skill only produces prompts).
- The request involves content blocked under **Security & Boundaries** that cannot be safely rewritten.
- `output/final-frames.json` already exists and `overwrite` is not `true` (stop with `OUTPUT_EXISTS`).


### Security & Boundaries
- **File writes:** Restricted to the workspace `output/` directory. Never write outside the skill root (e.g., `output/`, `output/final-frames.json`). A write outside `output/` stops the run with `PERMISSION_DENIED`.
- **Network access:** None. This skill performs no web access and no outbound calls.
- **PII / Secrets:** Do not persist credentials, tokens, or personal data in outputs.
- **Content safety:**
    - Copyrighted or branded characters and IP: replace with an original archetype (describe it, do not name it).
    - Apply this check in Step 1 (on the idea) and again in Step 5.2 (on final prompts).
- **Idempotency:** Existing output is never overwritten silently. Step 1 checks `get_file_info` first; files are replaced only when input `overwrite` is `true`, otherwise the run fails safely with `OUTPUT_EXISTS`.
- **Dependencies:** The LLM handles all logic via native tools (`read_files`, `write_file`, `get_file_info`, `ask_question`).


---


## 🧠 Core Philosophy


This skill operates on three guiding principles:


- **LLM-Centric:** The LLM is the "brain" that plans, executes, and verifies each phase.
- **Minimal Interaction:** Use `ask_question` ONLY when input is insufficient (max 2 calls total; see Step 2).
- **Zero Python/Scripting:** No inline code blocks or external scripts required for content generation.


> **Why?** Ensures the LLM remains in control of the workflow, reducing dependency on external tools and keeping execution transparent and self-contained.

## ⚙️ Operational Workflow


Execute these steps **sequentially**. Emit a status update only when a phase is long-running, blocked, or requires user input.


### 1. Validation Phase
- **Check:**
    - `idea` is present and non-empty (else `MISSING_INPUT`).
    - Run `get_file_info` on `output/final-frames.json` and `output/buffers/.drafting_state.json`.
    - Verify every template in the Resource Map is readable with `read_files` (else `TEMPLATE_NOT_FOUND`).
- **Config resolution (single rule, in this order):**
    1. Input `mode`, if provided.
    2. Else `frame_selection` from `config/config.yaml`, if the file exists and the value is valid.
    3. Else defaults (`firstmiddlelast`); record `"config_source": "defaults"` in the run report.
    - A missing config file is never a reason to stop or ask. An existing config with an invalid value stops the run with `INVALID_CONFIG`.
- **Existing output / resume:**
    - If `output/final-frames.json` exists and `overwrite` is not `true`: stop with `OUTPUT_EXISTS`.
    - If a state file exists with `status: "in_progress"` and its `idea_summary` matches the current idea: resume from `last_checkpoint` and skip completed phases.
    - If it does not match and `overwrite` is not `true`: stop with `OUTPUT_EXISTS`. If `overwrite` is `true`: start fresh.
- **Setup:** Write an empty `output/buffers/.keep` to ensure the buffer directory exists if `write_file` does not create parent folders.
- **Action:** Run the content safety check (see Security & Boundaries). If the idea is insufficient, handle it in Step 2 (it shares that question call).


### 2. Research & Gathering Phase (Interactive & Immersive)
- **Tools:** Use `read_files` on template schemas AND `ask_question` for story depth assessment.
- **Goal:**
    - Load template schemas from `assets/`.
    - Assess if the initial idea has sufficient narrative depth using ONE rule: the idea is **sufficient** if it is at least 50 words OR clearly contains all four of character, setting, conflict, and visual tone. Otherwise it is **insufficient**.
    - If insufficient, use `ask_question` to gather (all in a single batched call):
        - **Character Details** (Name, appearance, motivation)
        - **Setting Context** (Location, time period, atmosphere)
        - **Conflict/Plot** (Main challenge, stakes, resolution hint)
        - **Visual Tone** (Lighting style, color palette, mood)
- **Action:**
    - **Build the character bible:** for each recurring character and location write fixed descriptors (age range, build, hair, clothing, distinguishing marks, palette). Save to `output/buffers/character-bible.json`.
    - **Craft Immersive Narration:** Transform raw responses into a rich, cinematic story with:
        - **Sensory Details** (sight, sound, smell, touch, taste)
        - **Character Dialogues** (natural-sounding conversations between characters including internal thoughts)
        - **Internal Monologues** (thoughts and emotions of key characters)
        - **Atmospheric Descriptions** (weather, lighting, environment interactions)
    - Structure the narrative to flow naturally from scene to scene, with one clear beat per clip.
- **Output:** Synthesize received into a knowledge base for the Structuring Phase.
- **Limit (Question Budget):** Max 2 `ask_question` calls total across all phases.
    - **Call 1 (batched):** all missing items above in one call. Never ask per category.
    - **Call 2 (reserved):** one follow-up only if Call 1 answers are unusable.
    - Step 1 validation does not get its own call; it shares Call 1.
    - If still insufficient after the budget, proceed with stated assumptions saved to `output/buffers/assumptions.json`. Never ask a third time.


### 3. Structuring Phase
- **Logic:** Organize data into [Story Text] using `assets/formatted-story-template.md`.
- **Criteria:** Ensure the flow follows [Narrative Arc — e.g., Setup → Conflict → Resolution].
- **Action:**
    - Save the clean, human-readable story as `output/story.txt` using `write_file`.
    - Save the working copy with clip boundary markers (`[CLIP n]`) as `output/buffers/formatted-story.txt`.


### 4. Drafting Phase (Iterative & Timeout-Safe)
- **Logic:** Fragment story into clips/frames in small batches (max 3 clips per iteration). Target `clips_target` clips and `candidate_frames_per_clip` candidate frames per clip (see Input Specification, config).
- **State Tracking:** Use a lightweight state file (`output/buffers/.drafting_state.json`) to track:
    - Total clips processed
    - Clips with frames generated
    - Last checkpoint for timeout recovery
- **Timeout Safety:** Do not rely on time estimates. Rewrite the state file after **every batch**; that checkpoint is the only recovery mechanism. On startup, Step 1 checks for an existing state file and resumes from it.
- **Action:**
    - Read `assets/clipped-story-template.md` and `assets/clip-frames-template.md`.
    - Process first batch of clips → save as `output/buffers/clipped-story.json`.
    - Then process frames for each clip → save as `output/buffers/clipX-frames.json`.
    - Reuse character-bible descriptors verbatim in every frame's subject description.
- **Output:** Save intermediate results (`output/buffers/formatted-story.txt`) and JSON buffers.
- **State file schema:**
```json
{
  "status": "in_progress",
  "idea_summary": "one-line summary of the idea",
  "mode": "firstmiddlelast",
  "total_clips": 6,
  "clips_with_frames": [1, 2, 3],
  "last_checkpoint": "step4_batch2",
  "updated": "2026-10-15"
}
```
    Set `status` to `"complete"` when Step 5.2 finishes.


### 5. Processing Phase (LLM Execution)


#### 5.1 Selection Logic
- **Logic:** Use the mode resolved in Step 1 (`frame_selection`).
    - If `"firstmiddlelast"`: Use `assets/logic/firstmiddlelast_selection_logic.md` (3 frames per clip: first, middle, last by position; scoring decides which candidate fills each position).
    - If `"best"`: Use `assets/logic/peak_selection_logic.md` (1 peak frame per clip).
- **Command:** Apply weighted scoring formula: $Score = (Action \times 0.3) + (Visual \times 0.25) + (Lighting \times 0.15) + (Composition \times 0.15) + (Narrative \times 0.15)$
    - Every component is an integer **0-100**; the total is therefore 0-100.
    - Scoring anchors: **90-100** exceptional; **75-89** strong with minor weaknesses; **50-74** adequate but generic or partly unclear; **0-49** weak, missing, or contradicting the beat.
    - Save all five sub-scores and the total for every candidate to `output/buffers/scores.json`.
- **Validation:** Confirm selected frames meet threshold ($\ge$85.0, configurable via `score_threshold`).
- **If a selected frame is below threshold:**
    1. Redraft it up to 2 times: rewrite the frame description to improve its weakest component, rescore, and replace it in `clipX-frames.json`.
    2. If still below after 2 redrafts: with `strict_threshold: true` stop with `THRESHOLD_NOT_MET`; with `false` keep the highest-scoring candidate, set `"below_threshold": true` on it, and list it under `warnings` in the run report.
- **Output:** Use `write_file` to save `output/buffers/selected-frames.json`:
```json
{
  "mode": "firstmiddlelast",
  "threshold": 85.0,
  "selected": [
    { "clip": 1, "frame_id": "clip1-frame1", "position": "first", "score": 88.4, "below_threshold": false }
  ]
}
```
    Expected count: `clips_target x 3` for `firstmiddlelast`, or `clips_target x 1` for `best`. Verify the count matches before continuing.


#### 5.2 Final Assembly
- **Asset:** Read `assets/final-frames.template.json` and `assets/prompt-format.md` using `read_files`.
- **Action:** Process `output/buffers/selected-frames.json` by populating templates with frame data via LLM reasoning.
    - **positive:** character-bible descriptors (verbatim), action, setting, camera/shot type, lighting, palette, mood, and style tokens from `assets/prompt-format.md`. Must not exceed `max_prompt_chars`.
    - **negative:** defaults from `assets/prompt-format.md` plus frame-specific items.
    - **wh_ratio:** the config value (default `"16:9"`).
    - **Consistency:** identical appearance wording for the same character in every prompt.
    - **Self-contained:** each prompt works alone, with no "same as before" references.
    - Re-run the content safety check on the final prompts.
- **Command:** Use `write_file` to generate `output/final-frames.json` from selected frames and prompt format template. Also write the run report (see Output Specification) to `output/run-report.json`.
- **Validation:** Confirm the output file exists and is non-empty using `get_file_info`. (No exit code check needed — pure file I/O.) Set `.drafting_state.json` status to `"complete"`.
- **Final response to the user:** a short prose summary (what was made, mode used, frame count, any warnings, file locations) followed by the success JSON block.

## 📥 Input Specification


| Field | Type | Requirement | Description | Example |
|-------|------|-------------|-------------|---------|
| idea | String | Required | The core concept or scene description. | "A cyberpunk detective in a rainy alley" |
| mode | String | Optional | Override for `firstmiddlelast` or `best`. Resolved per the Step 1 config rule (input, then config, then defaults to `"firstmiddlelast"`). | "best" |
| overwrite | Boolean | Optional | Allow replacing existing output and stale state. Default `false`. | true |


### Config file: `config/config.yaml` (optional; defaults apply if absent)


```yaml
frame_selection: firstmiddlelast   # firstmiddlelast | best
clips_target: 6                    # allowed 3-10
candidate_frames_per_clip: 4       # allowed 3-6 (at least 3 for firstmiddlelast)
score_threshold: 85.0              # 0-100
strict_threshold: false            # true = fail if any selected frame stays below threshold
wh_ratio: "16:9"                   # aspect ratio used in every prompt
max_prompt_chars: 1000             # hard cap per positive prompt
```

### Worked Example (abbreviated)


**Input:** `idea`: "A cyberpunk detective in a rainy alley finds a glowing data chip." `mode`: `best`.

1. **Sufficiency:** under 50 words, no conflict or tone → one batched `ask_question`. Answer: "Mara Voss, 40s, silver bob, black trench; chip is stolen evidence; neon-noir."
2. **Character bible:** `Mara Voss, woman in her 40s, silver bob haircut, weathered face, long black trench coat with a high collar, cybernetic left eye with a faint amber glow`.
3. **Clips (6):** arrival, finding the chip, the hologram, a pursuer appears, the chase, the escape.
4. **Frames:** 4 candidates per clip. Clip 2: close-up of hand lifting chip, crouched medium shot, over-shoulder, wide alley.
5. **Selection (`best`):** close-up scores Action 80, Visual 92, Lighting 95, Composition 88, Narrative 85 → `0.3x80 + 0.25x92 + 0.15x95 + 0.15x88 + 0.15x85 = 86.2` (passes). 1 frame per clip, 6 total.
6. **Final prompt (clip 2):**
    - positive: `Mara Voss, woman in her 40s, silver bob haircut, weathered face, long black trench coat with a high collar, cybernetic left eye with a faint amber glow, crouching and lifting a glowing blue data chip from a rain puddle, narrow neon-lit alley, cinematic close-up, shallow depth of field, cyan and magenta rim lighting, wet reflective surfaces, neon-noir mood, highly detailed`
    - negative: `blurry, extra fingers, deformed hands, text, watermark, low quality`
    - wh_ratio: `16:9`

## ✅ Quality Checklist


Before confirming completion, verify (any failure stops with `VALIDATION_FAILED`):


- [ ] Check 1: Every JSON file written parses and contains the keys required by its template.
- [ ] Check 2: `output/story.txt` is non-empty and `formatted-story.txt` contains exactly `clips_target` clips.
- [ ] Check 3: `output/final-frames.json` contains valid prompt strings (non-empty, within `max_prompt_chars`).
- [ ] Check 4: Selection mode used (`firstmiddlelast` vs `best`) matches the Step 1 config resolution.
- [ ] **Check 5:** Verify `config/config.yaml`, if present, contains a valid `frame_selection` mode; if absent, defaults were recorded in the run report.
- [ ] **Check 6:** Confirm `.drafting_state.json` is updated after each batch in Drafting Phase and ends with `status: "complete"`.
- [ ] **Check 7:** Ensure all JSON buffers (`clipped-story.json`, `clipX-frames.json`, `selected-frames.json`) are non-empty before Final Assembly.
- [ ] **Check 8:** Selected frame count equals the expected count for the mode, and every frame scores at or above threshold or is flagged `below_threshold: true` and listed in `warnings`.
- [ ] **Check 9:** Every prompt contains the verbatim character-bible descriptors for each character in that frame.
- [ ] **Check 10:** `ask_question` was called at most 2 times.


> **Why?** Prevents premature completion with partial or corrupted data, ensuring downstream consumers receive valid inputs.
