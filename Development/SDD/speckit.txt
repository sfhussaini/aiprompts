## 🔄 Development Workflow Chain

The Speckit system follows this progression for each feature:

### Full Workflow Chain
```
User Request → /speckit.specify → Review spec → /speckit.plan → 
Research (Phase 0) → Design (Phase 1) → /speckit.tasks → 
/speckit.checklist → /speckit.implement → Final review
```

### Alternative Paths

**Clarification-First Path:**
```
User Request → /speckit.specify → /speckit.clarify (max 3 clarifications) → 
Updated spec → Review → Continue to planning phase
```

**Codebase Analysis Path:**
```
User Request → /speckit.analyze → Findings report → Follow-up actions
```

## 📦 Core Workflow Commands

### `/speckit.specify` - Feature Specification Generation
- **Purpose**: Create or update feature specification from natural language description
- **Output**: `specs/[N-feature-name]/spec.md`
- **Key Sections**:
  - User Scenarios & Testing (mandatory, prioritized P1/P2/P3)
  - Requirements (functional requirements FR-XXX)
  - Success Criteria (measurable, technology-agnostic)
  - Edge Cases
  - Assumptions

**Important Rules:**
- **Maximum 3 `[NEEDS CLARIFICATION]]` markers** - only for critical decisions lacking defaults
- **Priority order**: scope > security/privacy > user experience > technical details
- **Common reasonable defaults** (don't ask about these): data retention, performance targets, error handling, authentication method (OAuth2/session-based), integration patterns

### `/speckit.plan` - Implementation Planning
- **Purpose**: Execute planning workflow with research and design artifacts
- **Phases**:
  - **Phase 0 (Outline & Research)**: Generate `research.md` resolving all NEEDS CLARIFICATION
  - **Phase 1 (Design & Contracts)**: Generate `data-model.md`, `/contracts/*`, `quickstart.md`

**Output Artifacts:**
- `plan.md` - Technical implementation plan
- `research.md` - Technology decisions and alternatives
- `data-model.md` - Entity definitions and relationships
- `/contracts/` - Interface specifications
- `quickstart.md` - Validation guide for testing

### `/speckit.tasks` - Task Breakdown
- **Purpose**: Generate actionable, dependency-ordered tasks from design artifacts
- **Input**: plan.md, spec.md, data-model.md, contracts/, research.md, quickstart.md
- **Output**: `tasks.md`

**Task Format (REQUIRED):**
```
- [ ] T001 [P?] [Story?] Description with file path
```

**Components:**
- Checkbox: Always `- [ ]`
- Task ID: Sequential (T001, T002, T003...)
- [P] marker: Only if parallelizable (different files, no dependencies)
- [Story] label: Required for user story phases ([US1], [US2], etc.)
- Description: Clear action with exact file path

**Phase Structure:**
- Phase 1: Setup (project initialization)
- Phase 2: Foundational (blocking prerequisites - MUST complete before user stories)
- Phase 3+: User Stories in priority order (P1, P2, P3...)
  - Within each story: Tests → Models → Services → Endpoints → Integration
- Final Phase: Polish & Cross-Cutting Concerns

### `/speckit.checklist` - Quality Checklist Generation
- **Purpose**: Generate custom checklist for requirements quality validation
- **Concept**: Checklists are "UNIT TESTS FOR REQUIREMENTS WRITING"
- **What they validate**: Completeness, clarity, consistency, coverage of requirements
- **NOT for**: Testing implementation/verification ("Verify button clicks" ❌)

### `/speckit.clarify` - Requirement Clarification
- **Purpose**: Identify underspecified areas and ask targeted questions (max 5)
- **Expected to run BEFORE** invoking `/speckit.plan`
- Records clarifications directly in spec file

### `/speckit.implement` - Feature Implementation
- **Purpose**: Execute implementation plan by processing all tasks in tasks.md
- **Progress tracking**: Mark completed tasks as `[X]`
- **Validation**: Verify against specification, plan, and test coverage
- **Handles**: Parallel tasks ([P]), error reporting, completion validation

### `/speckit.analyze` - Codebase Analysis
- **Purpose**: Non-destructive cross-artifact consistency analysis
- **Scope**: spec.md, plan.md, tasks.md after task generation
- **Output**: Structured analysis report (read-only)
- **Detects**: Inconsistencies, duplications, ambiguities, underspecified items
- **Critical**: Constitution violations are always CRITICAL

## 🔧 Extension Hook System

**Configuration File**: `.specify/extensions.yml`

**Hook Structure:**
```yaml
hooks.before_specify:
  - extension: speckit.git.branch
    command: speckit.git-branch
    optional: true           # Won't block workflow
    description: Create feature branch

hooks.after_constitution:
  - extension: sync.notify
    command: sync-notify
    optional: true           # Notification after constitution update
```

**Hook Rules:**
- Hooks without `condition` field are executable (unless explicitly `enabled: false`)
- Non-empty `condition` values skip execution (leave to HookExecutor)
- Dotted command names convert to hyphens: `speckit.git.commit` → `/speckit.git-commit`
- **DO NOT** interpret or evaluate hook `condition` expressions
